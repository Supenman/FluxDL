# FluxDL 版本管理设计

> 目标：成品包内可直接查看版本、检查更新、看更新历史，并**一键更新**；
> 更新只替换发生变化的组件，不重下整个安装包；更新失败必须能自动退回可用状态。

## 1. 先说「增量」到底增量在哪

FluxDL 的体积构成决定了「整包重下」非常浪费：

| 组件 | 典型体积 | 变化频率 |
|---|---|---|
| `fluxdl.exe`（应用壳 + 前端资源） | 约 15 MB | 每次发版 |
| `tools/yt-dlp.exe` | 23 MB | YouTube 改版就变，几乎每周 |
| `tools/ffmpeg.exe` | 78 MB | 季度级 |
| `browser-extension/` | < 200 KB | 偶发 |

所以本方案不做二进制差分（bsdiff / zstd patch），而是做**组件级增量**：

- **应用更新**只下载 Release 里的单文件 `fluxdl.exe`（约 15 MB），不下载 47 MB 的 `Setup.exe`；
- **工具更新**由 `tools/` 独立管理，只下载变化的那一个工具，且支持多版本共存；
- 浏览器扩展随应用更新一起替换（体积可忽略）。

> 为什么不做字节级差分：需要为每个历史版本准备 patch、跨平台工具链复杂、
> 且杀软对「自己打补丁改自己」的行为很敏感。组件级替换已经能把 47 MB 降到 15 MB，
> 收益的大头拿到了，复杂度却低一个数量级。

**结论**：用户点「立即更新」= 下载 ~15 MB → 校验 → 重启生效。不重装、不重下 78 MB 的 ffmpeg。

## 2. 版本号命名规则

采用**语义化版本** `MAJOR.MINOR.PATCH[-prerelease][+build]`：

| 段 | 何时递增 | 例子 |
|---|---|---|
| `MAJOR` | 不兼容改动（任务文件格式、清单 schema 变更） | `0.x` → `1.0.0` |
| `MINOR` | 向后兼容的新功能 | `0.1.0` → `0.2.0`（本次） |
| `PATCH` | 向后兼容的问题修复 | `0.2.0` → `0.2.1` |

补充规则：

- **预发布**：`0.2.0-beta.1` 优先级**低于** `0.2.0`，稳定通道不推送；
- **build 元数据**（`0.2.0+abc123`）不参与比较；
- **缺段补齐**：`0.2` 视为 `0.2.0`；
- **拒绝非法输入**：`1.2.3.4`、`garbage` 解析失败，不会误判为「有新版本」；
- 工具版本不做强约束（yt-dlp 是 `2025.11.01` 日期版本），统一走「逐段数值比较」兜底。

实现位置：`crates/download-engine/src/update.rs` 的 `Version` / `version_is_newer`，
单测 `semver_ordering_follows_spec` 覆盖 9 种边界（含 `beta.10 > beta.9`）。

## 3. 磁盘布局

```
<localAppData>/tools/                    # 可写，安装版也在用户目录
  yt-dlp-2025.11.01.exe                  # 单文件，版本号进文件名
  ffmpeg-9.0/ffmpeg.exe (+ *.dll)        # 目录，shared 版需要同目录 dll
  tool-state.json                        # 激活版本 / 上一版本 / 已装列表

<appData>/update-state.json              # 待完成的替换现场（崩溃恢复依据）
<appData>/update-cache.json              # 版本清单缓存（6 小时）
<exe 同目录>/fluxdl.exe.new              # 已下载待替换
<exe 同目录>/fluxdl.exe.bak              # 替换前的备份（回滚来源）
```

> `tools/` 从「随包只读目录」复制到 `%LOCALAPPDATA%` 是必要前提：
> 安装版装在 `Program Files` 下，只读，无法就地更新工具。
> 首次启动时 `ensure_managed_tools()` 完成复制并登记版本，随包文件退化为「初始来源」。

## 4. 更新记录的数据结构

清单是一个 JSON，应用本体、工具、历史三合一，客户端只读它。

```json
{
  "schema": 1,
  "app": {
    "latest": "0.2.0",
    "minSupported": null,
    "releasedAt": "2026-11-06T08:30:00Z",
    "notes": ["设置页新增版本管理", "更新失败自动回滚"],
    "assets": {
      "windows-x64": {
        "url": "https://github.com/Supenman/FuxDL/releases/download/v0.2.0/fluxdl.exe",
        "size": 15728640,
        "sha256": "9f2c..."
      }
    }
  },
  "tools": {
    "yt-dlp": { "latest": "2025.11.01", "versions": [] },
    "ffmpeg": { "latest": "9.0", "versions": [] }
  },
  "history": [
    {
      "version": "0.2.0",
      "releasedAt": "2026-11-06T08:30:00Z",
      "channel": "stable",
      "notes": ["设置页新增版本管理", "更新失败自动回滚"]
    }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema` | number | 清单格式版本，当前 1；不兼容变更时递增并拒绝旧客户端 |
| `app.latest` | string | 最新稳定版本号 |
| `app.minSupported` | string \| null | 低于它必须强制更新（协议不兼容时用） |
| `app.releasedAt` | ISO8601 | 发布时间，界面直接展示 |
| `app.notes` | string[] | 本次更新说明，界面取前 5 条 |
| `app.assets.<platform>` | object | `url` / `size` / `sha256`；`size` 与 `sha256` 至少要有 `sha256` |
| `tools.<name>.latest` | string | 该工具当前推荐版本 |
| `tools.<name>.versions` | array | 预留：由发布脚本写入可选版本（可为空，客户端会实时查 GitHub） |
| `history[]` | array | 版本号 / 发布时间 / 通道 / 说明，新→旧 |

**sha256 是强制的**：清单里缺 `sha256` 时客户端直接拒绝该更新（fail-closed），
宁可更不了，也不装一个「来源不明」的可执行文件。

## 5. 应用更新流程

```
检查 → 下载到 .new → 校验 → 写状态 → [重启] → 脚本替换 → 启动校验
```

1. **检查**：拉清单（Release 附件 → 仓库 raw → 镜像），6 小时内复用缓存；
2. **下载**：流式写入 `fluxdl.exe.new`，进度经 `update:progress` 事件推给界面；
3. **校验**：`size` + `sha256` 双重校验，任一不符立即删除 `.new` 并报错；
4. **写状态**：`update-state.json` 记录 `target / backup / staged / expect_sha256`；
5. **重启**：Windows 无法覆盖运行中的 exe，生成延迟脚本后退出进程；
6. **替换脚本**（`cmd`）：
   ```
   ping -n 4 127.0.0.1 >nul          # 等旧进程彻底退出
   move /y fluxdl.exe fluxdl.exe.bak
   move /y fluxdl.exe.new fluxdl.exe
   if not exist fluxdl.exe  → 把 .bak 还原回去
   start "" fluxdl.exe
   del "%~f0"
   ```
7. **启动校验**：见下一节。

## 6. 更新失败自动回滚

回滚不是「事后补救」，而是替换前就先留好退路。`update::recover()` 在每次启动时执行：

| 场景 | 判定依据 | 处理 | 用户看到 |
|---|---|---|---|
| 替换成功但状态文件没清 | `exe` 的 sha256 == `expect_sha256` | 删备份、删暂存、清状态 | Toast「已应用上次下载的更新」 |
| 脚本没跑（进程被强杀） | sha256 不符，`exe` 仍在 | 删暂存、清状态，保持旧版 | Toast「更新未完成，已回滚」 |
| 新版本文件损坏 | sha256 不符且 `.bak` 存在 | 用 `.bak` 覆盖回 `exe` | 同上 |
| 替换到一半断电 | `exe` 不存在但 `.bak` 存在 | 从 `.bak` 恢复 | Toast「更新未完成，已回滚」 |
| 脚本内替换失败 | `if not exist` 分支 | 脚本自己还原 `.bak` | 直接正常启动旧版 |

备份始终与主文件同目录（同卷），保证 `rename` / `move` 是原子的。

端到端验证在 `crates/download-engine/tests/update_recovery.rs`：
真实文件、真实 sha256、真实 `rename`，5 个场景全绿（含「新版本损坏后回滚」）。

## 7. 工具版本管理（yt-dlp / ffmpeg）

设置页「视频下载」一节各有一行版本选择器：

- **下拉列表**：已安装版本 + 远端可选版本（远端按 `- 使用中 / 已安装 / 体积` 标注）；
- **切换到此版本**：已装版本直接改 `EngineOptions` 指向并落盘；
- **下载并切换**：未装版本先下载（ffmpeg 会解压 `bin/` 下的 exe + dll），
  探测 `--version` 成功才登记，失败即删除；
- **回滚**：切回 `previous`（上一次激活过的版本），`ToolState` 持久化保证重启后仍可回滚；
- **刷新**：重新拉远端列表（进程内 10 分钟缓存，避免打满 GitHub 未登录限流 60 次/小时）。

版本来源：

| 工具 | 来源 | 说明 |
|---|---|---|
| yt-dlp | `api.github.com/repos/yt-dlp/yt-dlp/releases` | 取最近 12 个正式版，过滤 draft / prerelease，资产名 `yt-dlp.exe` |
| ffmpeg | `api.github.com/repos/BtbN/FFmpeg-Builds/releases/tags/latest` | 只取 `win64-lgpl-shared` 变体（73 MB，完整版 186 MB） |

激活前会实际执行一次工具并比对版本号，**探测失败拒绝切换**——不会把下载功能切到跑不起来的文件上。

## 8. 界面：更新提示的样式与交互

**主界面顶部横幅**（`UpdateBanner`）：

- 出现条件：`check.available == true` 且用户没有对**这个版本**点过「稍后」；
- 视觉：accent 渐隐背景 + 1px accent 下边框 + 顶部下滑 240ms 动效；
  「已下载待重启」状态切成蓝色（`--blue`）区分；
- 内容：`发现新版本 0.2.0` + 体积标签 + 第一条更新说明；
- 操作：`立即更新`（下载中变成百分比进度）/ `×`（稍后，仅对该版本生效）；
- 进度条：3px，`update:progress` 驱动，校验阶段显示「校验中」。

**设置页「版本与更新」**：

- 四宫格：当前版本 / 引擎版本 / 运行平台 / 交付方式（安装版 or 便携版）；
- 有更新：accent 描边卡片，列出最多 5 条说明 + 发布时间 + 体积 + `下载并安装`；
  `minSupported` 触发时卡片转红并标「必须更新」；
- 无更新：`已是最新版本（v0.2.0）`；
- 拉取失败：灰色提示 + 原因 + 「恢复网络后重试」，不弹错误对话框；
- 版本号规则：虚线卡片常驻说明语义化版本；
- 更新历史：折叠时间线，第一条高亮，展示版本号 / 日期 / 通道 / 逐条说明。

所有颜色只用 `app.css` 里已有的 CSS 变量（`--accent`、`--blue`、`--danger`、`--panel-2` 等），无新增硬编码色值。

## 9. 更新入口的触发时机

| 时机 | 行为 | 是否打扰 |
|---|---|---|
| 应用启动 +4 秒 | 静默检查（跳过缓存则用缓存） | 否；仅在有更新时显示横幅 |
| 启动时 `recover_on_startup` | 处理上次未完成的替换 / 回滚 | 仅在有结果时 Toast |
| 设置页点「检查更新」 | `force=true` 跳过 6 小时缓存 | 是；无更新也提示「已是最新」 |
| 打开设置页 | 读缓存 + 拉历史（不强制联网） | 否 |
| 切回任务列表 | 不重新检查（复用 store 状态） | 否 |

启动检查刻意延后 4 秒：避免和首屏任务列表、扩展资源嗅探抢带宽。

## 10. 发布流程

```bash
# 1) 改版本号（三处，必须一致）
#    src-tauri/tauri.conf.json · src-tauri/Cargo.toml · crates/download-engine/Cargo.toml · package.json

# 2) 构建
cd fluxdl/src-tauri && cargo xwin build --release --target x86_64-pc-windows-msvc

# 3) 生成清单（自动算 size + sha256，累积历史）
python3 tools/build-update-manifest.py \
  --version 0.2.0 \
  --exe src-tauri/target/x86_64-pc-windows-msvc/release/fluxdl.exe \
  --notes "设置页新增版本管理" "yt-dlp / ffmpeg 支持多版本切换与回滚" \
  --tool yt-dlp=2025.11.01 --tool ffmpeg=9.0 \
  --out update-manifest.json

# 4) 上传 Release：fluxdl.exe + update-manifest.json（+ 安装包与校验和）
# 5) 把 update-manifest.json 提交到仓库根，作为 Mirror / 兜底来源
```

清单的三个来源按顺序尝试，任一成功即用：
1. `releases/latest/download/update-manifest.json`（随版本发布）
2. `raw.githubusercontent.com/.../main/update-manifest.json`（仓库内）
3. `ghfast.top/https://raw.githubusercontent.com/...`（国内镜像）

## 12. 已知限制

- **Windows 自替换依赖脚本**：进程退出后由 `cmd` 完成替换，若用户在脚本执行前
  强杀进程，下次启动会判定「更新未完成」并保持旧版（不会坏，但需要重新点更新）。
- **签名**：当前包未做代码签名，`fluxdl.exe` 被替换后部分杀软可能重新扫描；
  首启稍慢属正常。
- **真实网络风控**：更新走 GitHub，国内可能需要代理（已内置镜像回退）。
- **ffmpeg 版本列表**只列 BtbN 的 `lgpl-shared` 变体；若需要特定构建（如 full build），
  仍可通过「ffmpeg 路径」手动指定。
- 工具的「选版本」依赖远端 API；完全离线时只能看到本地已装版本（界面会明确提示）。
