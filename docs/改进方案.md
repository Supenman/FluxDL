## 一、结论先行

项目工程质量**高于同类个人项目**：多段并发用 `pwrite`/`seek_write` 定位写、`SlotGuard` 用 RAII 管并发槽位、`CancellationToken` 贯穿全链路、限速用「时刻表」保证长期均值、持久化用临时文件原子替换。这些是下载器真正难做对的地方。

但有 **3 个会静默损坏用户文件 / 泄漏磁盘的缺陷**，本次已在本地**用测试实机复现**，不是推测：

| 编号 | 级别 | 问题 | 实测证据 |
|---|---|---|---|
| **P0-1** | 🔴 数据损坏 | 并发添加同名任务时，两个任务被分配到**同一个** `payload.bin`，共享同一个 `.fluxdl-part` | A、B 的 `save_path` **完全相同**，测试失败 |
| **P0-2** | 🔴 数据损坏 | 续传时只信 `tasks.json` 里的分段进度，不看磁盘 part 是否还在 | 暂停时下了 621 KB，删掉 part 后续传完成，**4 MB 文件里 766 KB 是 0** |
| **P1-4** | 🟠 磁盘泄漏 | `remove(delete_file=true)` 只删最终文件，不删 `.fluxdl-part` | 暂停中删除任务后 part **仍在** |

> 验证方式：`cargo test --test regression` 在**原始代码**上实测 —— **4 个用例失败**（缺陷复现成功），2 个通过。通过的两个里，`baseline_*` 是反例保护（正常的「part 还在时续传」没有误伤），`p0_1c` 是防回归用例（原始代码本来没有占位机制，天然通过；它的作用是防止我引入 `reserved` 后把「删文件重下」这条路径弄坏——第一版补丁正是坏在这里）。修复后 6 个全绿。

另外两项**未能实机验证**、只做静态判断，需注明：

- **P0-3（安全）**：本地 `127.0.0.1:35917` 用固定 token `fluxdl-local-v1` + `Access-Control-Allow-Origin: *`。任意网页可跨域调用，把你指定的文件静默下载到「下载」目录。**这条无法在本环境验证**（需要 Windows 桌面运行时），但代码逻辑是确定的，建议按最高优先级处理。
- **P1-5（`save()` 并发写）**：与 `store.rs` 的 tmp+rename 组合会产生写竞争。属于时序问题，静态分析成立，但复现成本高，建议直接按方案加固而不必先复现。

## 二、修复方案（按优先级）

### 🔴 P0-2：续传前必须校验磁盘 part 文件

**根因**：`effective_resume` 全部依据持久化元数据判定，而 part 文件是 `OpenOptions::create(true)` 打开的——文件不在就会被**新建一个空文件**，紧接着 `set_len(total)` 把它拉成等长的稀疏文件（全是 0）。此时分段表里那些 `done` 的分段被跳过，空洞永远补不上。

**改法**：把「能不能续」的判定从"信元数据"改为"信磁盘"。**位置很关键——必须在「规划分段」之前**，否则分段已按旧进度生成，后面再重置就是全 0 分段。

```rust
// http.rs::run —— 必须插在 `let mut segments: Vec<SegmentView> = ...` 之前
let part_path = PathBuf::from(format!("{}.fluxdl-part", save_path.to_string_lossy()));
if effective_resume {
    let part_len = std::fs::metadata(&part_path).map(|m| m.len()).unwrap_or(0);
    if renamed || total == 0 || part_len != total {
        effective_resume = false;
        entry.downloaded.store(0, Ordering::Relaxed);
        entry.segments.lock().clear();   // 丢弃陈旧进度，让下游重新 plan
    }
}
```

> ⚠️ **实测踩坑记录**：我第一版补丁把这段插在了分段规划**之后**（只是因为那里已经有 `part_path` 变量），结果测试从"766 KB 补零"变成"整文件全 0"——因为 `segments` 已被填好又被清空，却没有重新生成。移到规划之前后通过。**这个顺序就是修复的成败点**，务必注意。

**要点**：
1. `renamed == true` 时必然是新目标，不能续。
2. `total == 0`（服务器不给长度）无法校验，按不可续处理。
3. `effective_resume` 变 false 后，原有的"删旧 part + 重建 + 重新 plan_segments"逻辑会自动生效，不需要额外写。
4. 更彻底的方案是加 sidecar（`.fluxdl-state`）记录每段完成状态 + 远端 `ETag`/`Last-Modified`，续传前比对。这能额外解决"服务端文件已变更"的陈旧续传问题，建议作为下一迭代。

**验收**：`p0_2_resume_after_part_deleted_must_not_corrupt` 由失败转通过；`baseline_resume_with_part_present_is_correct` 保持通过。

### 🔴 P0-1：目标路径必须在分配时占位

**根因**：`unique_path` 只判断 `final_path.exists()`，而真正的写入文件是 `{save_path}.fluxdl-part`，且要到 `http::run`（另一个 spawned task）才创建。两个 `add()` 之间的窗口期，后一个仍看到"文件不存在"。

**改法**：在 `Engine` 里维护"已占用路径"集合，分配时在**同一把锁内**占位；`unique_path` 同时检查 `.fluxdl-part`。关键是这个占位有完整的生命周期，不只是"插入"。

```rust
// manager.rs —— Engine 新增字段
/// 已分配给任务的目标路径。unique_path 只判断最终文件是否存在，
/// 而写入用的是 `{save_path}.fluxdl-part`，在 part 创建前存在竞态窗口。
reserved: Mutex<std::collections::HashSet<PathBuf>>,
```

```rust
// manager.rs::add —— 分配与占位在同一把锁内完成
let save_path = {
    let mut reserved = self.reserved.lock();
    let candidate = util::unique_path_reserved(&dir, &filename, &reserved);
    reserved.insert(candidate.clone());
    candidate
};
```

```rust
// util.rs —— 把 part 纳入判断，并支持「已被其它任务占用」的集合
pub fn unique_path_reserved(
    dir: &Path,
    filename: &str,
    reserved: &std::collections::HashSet<PathBuf>,
) -> PathBuf {
    let taken = |p: &Path| -> bool {
        if p.exists() {
            return true;
        }
        // 进行中的任务只写了 part，最终文件还不存在，但路径已被占用
        PathBuf::from(format!("{}.fluxdl-part", p.to_string_lossy())).exists()
    };
    // ... 逐个尝试 `name`、`name (1)`、`name (2)`，同时避开 taken 与 reserved
}
```

**占位的完整生命周期**（三处缺一不可，我第一版只做了插入，被自测抓出来）：

| 时机 | 动作 | 漏掉的后果 |
|---|---|---|
| `add()` | 锁内分配 + 插入 | 并发 add 撞同一路径 |
| `Engine::new()` hydrate | 把 `tasks.json` 里恢复的任务路径**重新插入** | 重启后 part 尚未创建时，新任务与恢复任务撞车 |
| 任务 `Completed` / `Failed` | 释放 | 用户删掉文件重下，名字被永久挤成 `file (1)` |
| `remove()` | 释放 | 删除任务后路径永久占用 |

> `Paused` 状态**不能**释放——暂停的任务仍持有 part，要继续占着这个路径。

**验收**：`p0_1`（并发）、`p0_1b`（重启）、`p0_1c`（终态释放）三个用例全部通过，且原有 5 个集成测试不受影响。

**这版的残余窗口**（已知，可接受）：`http.rs:158` 处理"服务器改名"时调用的是无 reserved 的 `unique_path`，理论上仍可能与刚 add 但尚未创建 part 的任务撞名。该分支只在 `Content-Disposition` 给出意外文件名时走到，概率低；彻底消除需要把 reserved 引用传进 `run`，属于下一迭代。

### 🟠 P1-5：`save()` 并发写竞争 —— 已在 `bbd1867` 修复

**比静态判断更严重**：实测 32 次并发 `save()` 后 **`tasks.json` 整个文件消失**，不是内容损坏。
根因是 `store::save` 用固定 `tasks.json.tmp` + 「先删目标再 rename」：并发调用互相踩 tmp，
后一个 `rename` 找不到 tmp，而目标已被前一个删掉，任务列表凭空消失。

**实际修复**（两层，分别反向验证过必要性）：

```rust
// manager.rs —— 在收集快照之前就持锁
pub async fn save(&self) {
    let _guard = self.save_lock.lock().await;
    // ...原有构建 store 的逻辑...
}
```

```rust
// store.rs —— 不再先删目标；tmp 带 pid；rename 失败时清理自己的 tmp
let tmp = path.with_file_name(format!("{}.{}.tmp", file_name, std::process::id()));
tokio::fs::write(&tmp, raw).await?;
match tokio::fs::rename(&tmp, path).await {
    Ok(()) => Ok(()),
    Err(err) => { let _ = tokio::fs::remove_file(&tmp).await; Err(err) }
}
```

直接 `rename` 覆盖的依据是 [`std::fs::rename` 文档](https://doc.rust-lang.org/std/fs/fn.rename.html)：
「replacing the original file if `to` already exists」，Windows 走 `MoveFileExW`。
失败时旧文件保持原样，不再有「删了却没改名回来」的窗口。

**反向验证**：只保留原子 rename、撤掉 `save_lock` → 立刻复现写竞争；两层都在 → 通过。
未做「去抖」（`tick` 每 5 秒落盘 + 操作点落盘，加锁后频率已可控，去抖会引入额外复杂度）。

### 🟠 P1-6：`spawn_runner` 检查与置位合并 —— 已在 `bbd1867` 修复

原实现「先读 `cancel` 判断有没有在跑，隔了几个 `await`，再写新 token」。并发 `resume()` 会
各自启动一个 runner，后写的 token 覆盖前一个；`pause()` 只取消得到最后一个，旧 runner 继续下载。

**实际修复**：把 Completed 检查提前，然后在**同一个 `cancel` 锁临界区**内完成「判断 + 置位」，
之后才更新 view 状态与 emit。

```rust
let token = CancellationToken::new();
{
    let mut cancel = entry.cancel.lock().await;
    if cancel.as_ref().map(|t| !t.is_cancelled()).unwrap_or(false) { return; }
    *cancel = Some(token.clone());   // 检查与置位在同一临界区
}
```

该窗口很窄，回归用例 `p1_6_concurrent_resume_keeps_pause_effective` 是**防御性保护，
未能在旧代码上稳定复现**，如实标注，不假装它能证明缺陷。

### 🟠 probe 首次失败即放弃 —— 已在 `bbd1867` 修复

`http.rs::probe` 只发一次 `RANGE: bytes=0-0`，网络抖动或临时 5xx 就把整个任务判失败，
而分段下载本身有 `RETRIES` 重试。修复：网络错误 / 超时 / 5xx 按与 `segment_loop` 一致的
指数退避重试 `RETRIES` 次；4xx 等确定性错误直接返回。

复现稳定：测试服务器前 2 个请求返回 500，修复前任务直接 `Failed`，修复后完成下载且内容一致。

## 六、第三轮：扩展 v2 与内置工具（已合并 main）

需求来自用户的三条明确反馈：**接管范围不该让用户设置**、**不要「下载当前页面」**、**要像 IDM 一样自动找页面上的音视频等资源**；另外提出 `yt-dlp` / `ffmpeg` 体积可接受就直接内置。

### 6.1 改动清单

| 位置 | 改动 |
|---|---|
| `browser-extension/background.js` | 删除扩展名白名单 / 类型分组 / `minSizeMB`；`shouldCapture` 只剩总开关 + http(s) 判断。新增 `webRequest.onResponseStarted` 按 `Content-Type` / `Content-Disposition` / URL 后缀嗅探资源，按 tab 存入 `storage.session` |
| 同上 | `.m4s` / `.m3u8` / `.mpd` 与 DASH/HLS 清单判为 `stream`，不列为普通文件，只标记「本页有视频」；视频站点由弹窗发 `kind: "media"` 交给桌面端 `yt-dlp` |
| 同上 | 删除 `MENU_PAGE`（用 FluxDL 下载当前页面），保留「下载此链接」，新增「下载此媒体」 |
| `popup.html/js/css` | 删除「自动接管范围」「跳过小文件」控件；新增视频卡片、本页资源列表、清空 / 全部发送 |
| `src-tauri/src/lib.rs` | 新增 `bundled_tools_dir` / `bundled_tool_paths` / `apply_bundled_tools`，setup 时自动把 `EngineOptions` 指向随包 `tools/`；用户手填且真实存在的路径优先。`install_tools` 优先用随包二进制，探测成功即不联网 |
| `src-tauri/tauri.conf.json` | 增加 `../tools": "tools/"` 资源映射 |
| `tools/`、`.gitignore` | `README.md` + `fetch-tools.sh`；二进制只进成品包不进 Git |

**二进制不进 Git 的理由**：四个文件合计约 268 MB，其中 Linux `ffmpeg` 单文件 165 MB，超过 GitHub 单文件 100 MB 上限。仓库只留获取脚本，成品包里才带二进制，且按平台各放各的两个（Windows 包不放 Linux 版，反之亦然）。

### 6.2 端到端跑出来的两个真实缺陷（已修）

1. **资源缓存并发覆盖**：`addResource` 是 `读 storage → await → 写 storage`，页面里多个响应几乎同时到达时，几个调用都读到同一份旧列表，后写的把先写的整份冲掉。实测同一测试页嗅探结果在 3 / 2 / 0 个之间随机跳。改为用一条 Promise 链把 `addResource` / `markStream` / `clearTab` 全部串行化；同时 `tabs.onUpdated` 改为「只在 URL 真的变化时清缓存」，避免同一次导航重复清空。
2. **`[hidden]` 被类样式覆盖**：`popup.css` 里 `.video-card { display: flex }` 优先级高于 UA 的 `[hidden] { display:none }`，导致「本页检测到视频」卡片和「全部发送」按钮永远显示。补 `[hidden] { display: none !important }`。

### 6.3 验证结果

- 扩展核心纯函数 Node 单测 **22/22**（接管、分类、视频站点识别、文件名解析）。
- **真实 Chrome for Testing 145 + MV3 unpacked 扩展端到端 18/18**：service worker 加载、资源嗅探、流媒体标记、popup 经 `chrome.runtime` 消息渲染、hidden 修复、media 任务入队、1 KB 小文件自动接管、浏览器原生下载被取消。
  - 过程中纠正了一个环境误判：正式版 Chrome 144 会静默忽略 `--load-extension`（profile 里查不到 unpacked 记录），先前看到的 `service_worker` 其实是 Chrome 内置组件。必须换 Chrome for Testing 并加 `--enable-unsafe-extension-debugging`。
  - 另一次失败是检查脚本把持久化结构 `{"view":{...},"options":{...}}` 当扁平对象读，导致误报「未入队」；修正后 `tasks.json` 里能看到 `kind: media` 与 `demo.txt` 两个真实任务。
